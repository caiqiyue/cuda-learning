## 1. 为什么要配置这个环境

此前主要用 Python 进行机器学习和 AI 开发，接下来要进入底层推理 / 量化开发。`llama.cpp`、`ggml` 等项目涉及大量 C/C++ 代码、编译工具、内存管理与底层算子。

第一阶段的目标非常具体：

1. 在 **VS Code** 中编写 `.cpp` 源文件；
2. 用 **G++** 完成编译、链接，生成 Windows `.exe`；
3. 在 **PowerShell** 中运行程序；
4. 安装好 **GDB**，为后续断点调试打基础；
5. 学会独立排查“编译工具存在，但编译失败”的环境问题。

### 1.1 每个工具分别负责什么

| 工具 / 组件 | 主要作用 | 需要区分的点 |
|---|---|---|
| VS Code | 编辑器、文件管理、集成终端、调试界面 | VS Code **自身不是** C++ 编译器 |
| Microsoft C/C++ 插件 | IntelliSense、代码导航、调试集成 | 安装插件 ≠ 已安装 G++ |
| MSYS2 | Windows 上的软件包管理与开发环境 | 提供多个工具链环境；本次选择 **UCRT64** |
| `gcc` | GNU 编译器驱动，通常用于 C | 编译 C++ 优先使用 `g++` |
| `g++` | GNU C++ 编译驱动，组织编译、汇编和链接 | 它还会调用其他子程序 |
| `cc1plus.exe` | GCC 的 C++ 编译前端 | 本次故障的关键报错发生在这里 |
| `as.exe` | 汇编器 | 生成目标文件 `.o` |
| 链接器（`ld` 等） | 将目标文件和库组合为可执行文件 | 并非 `g++` 自己完成全部处理 |
| `gdb` | C/C++ 调试器 | 后续用来打断点、查看变量与调用栈 |
| PowerShell | 执行命令的 Shell | 它运行的环境变量可能与新终端不同 |

### 1.2 一句话理解整个过程

```text
VS Code 写 hello.cpp
         ↓
PowerShell 执行 g++
         ↓
GCC 工具链执行编译、汇编、链接
         ↓
生成 hello.exe
         ↓
Windows 执行 hello.exe
```

### 2.1 选择 MSYS2 安装包

> 注：上面两种文件名来自本次下载页面截图；官网后续可能提供更新的安装包。

### 2.2 安装 MSYS2

双击下载的 `.exe`，按向导安装。建议保留默认目录：

```text
C:\msys64
```

本次使用的工具链最终安装到了：

```text
C:\msys64\ucrt64\bin
```

安装完毕后，从 Windows 开始菜单打开 **MSYS2 UCRT64** 终端。不要把普通 `MSYS2 MSYS` 终端与 `MSYS2 UCRT64` 混淆。

#### UCRT64 是什么？

UCRT64 是 MSYS2 的一个 Windows 原生 x64 工具链环境，使用 UCRT（Universal C Runtime）及相应的 GCC / MinGW-w64 工具。它不同于 MSYS2 用于 POSIX 风格工具的 `/usr` 环境。

本次选用 UCRT64，因此后面的编译器路径包含 `ucrt64`。

### 2.3 更新 MSYS2 软件包

在 **MSYS2 UCRT64** 中运行：

```bash
pacman -Syu
```

- `pacman`：软件包管理器；
- `-S`：软件包同步/安装相关操作；
- `-y`：刷新软件包数据库；
- `-u`：升级已安装软件包。

如果提示关闭并重新打开终端，就按提示操作并继续更新。

> 此步骤是本次推荐的安装流程；未保存完整更新日志，不能据此判断每个包的具体更新情况。

### 2.4 安装 C/C++ 工具链

仍在 **MSYS2 UCRT64** 中运行：

```bash
pacman -S --needed base-devel mingw-w64-ucrt-x86_64-toolchain
```

命令解释：

| 片段 | 解释 |
|---|---|
| `pacman -S` | 安装 / 同步软件包 |
| `--needed` | 已满足需求的包不重复安装 |
| `base-devel` | 基础构建工具集合 |
| `mingw-w64-ucrt-x86_64-toolchain` | UCRT64 的 GCC / G++ / GDB 等工具链包组 |

如果询问安装哪些包，通常直接 Enter 接受默认的全部选择；确认安装时输入 `Y`。

**本次实际日志证明 G++ 已安装**，版本为：

```text

gcc version 16.2.0 (Rev6, Built by MSYS2 project)
```

### 2.5 配置 VS Code

如果已经安装 VS Code，则无需重装。按 `Ctrl + Shift + X` 打开扩展面板，搜索：

### 2.6 最初配置 PATH

## 4. 故障现象

### 4.1 初始故障

在 VS Code / PowerShell 中执行：

```powershell
g++ hello.cpp -o hello.exe
ls
```

终端未显示明显的编译错误，但 `ls` 仍然只有：

```text
hello.cpp
```

**关键异常：没有出现 `hello.exe`。**

这并不是“没有输出就代表编译成功”。很多编译器在成功时确实安静无输出，但是否成功要结合退出码和目标文件判断。

### 4.2 加上 `-v` 查看调用过程

运行：

```powershell
g++ -v .\hello.cpp -o .\hello.exe 2>&1
```

终端看到的关键信息：

```text
COLLECT_GCC=C:\msys64\ucrt64\bin\g++.exe
COLLECT_LTO_WRAPPER=...\16.2.0\lto-wrapper.exe
Target: x86_64-w64-mingw32
gcc version 16.2.0 (Rev6, Built by MSYS2 project)
...
C:/msys64/ucrt64/bin/../lib/gcc/x86_64-w64-mingw32/16.2.0/cc1plus.exe ... hello.cpp ...
```

接下来没有看到完整的汇编、链接、输出文件生成过程。

**分析**：`g++` 驱动本身能够启动，但它启动的 C++ 前端 `cc1plus.exe` 可能出了问题。

> 当时 PowerShell 还显示过 `NativeCommandError`、`Using built-in specs.`。由于 `g++ -v` 把正常诊断信息写到标准错误流，`2>&1` 合并后可能被 PowerShell 包装为错误对象；**仅凭这段红字不能判断具体故障**。真正有价值的是后面的退出码和直接运行 `cc1plus.exe` 的结果。

### 4.3 读取退出码与检查文件

```powershell
g++ hello.cpp -o hello.exe
$LASTEXITCODE
Test-Path .\hello.exe
```

实际输出：

```text
1
False
```

解读：

- `$LASTEXITCODE = 1`：上一条原生程序命令执行失败；
- `Test-Path = False`：输出文件确实不存在。

### 4.4 直接检测 C++ 编译前端

运行：

```powershell
& "C:\msys64\ucrt64\lib\gcc\x86_64-w64-mingw32\16.2.0\cc1plus.exe" --version
$LASTEXITCODE
```

实际输出：

```text
-1073741511
```

这一步非常关键：即使只要求 `cc1plus.exe` 打印版本号，它也未能正常完成。这使我们不再优先怀疑 `hello.cpp` 代码错误。

Windows 的错误码转换：

```text
-1073741511（有符号十进制）
       = 0xC0000139（十六进制 NTSTATUS）
       = STATUS_ENTRYPOINT_NOT_FOUND
```

微软的定义是：**找不到所加载动态链接库中需要的过程 / 函数入口点**。

### 4.5 用临时 PATH 修改做对照实验

在**同一个 PowerShell** 中执行：

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
```

马上重新测试：

```powershell
& "C:\msys64\ucrt64\lib\gcc\x86_64-w64-mingw32\16.2.0\cc1plus.exe" --version
$LASTEXITCODE
```

实际得到：

```text
0
```

随后再编译：

```powershell
g++ .\hello.cpp -o .\hello.exe
$LASTEXITCODE
Test-Path .\hello.exe
```

实际得到：

```text
0
True
```

最后运行：

```powershell
.\hello.exe
```

实际输出：

```text
Hello, C++!
```

**这一组对照最有说服力：在不修改源代码、也不重装编译器的情况下，只改变 PATH 优先级，就恢复了 `cc1plus.exe` 和 G++ 的正常运行。**

### 4.6 最初修改“用户 Path”为什么没有奏效？

后来截图已经显示：虽然 `C:\msys64\ucrt64\bin` 被放在环境变量编辑窗口的最上面，但新 PowerShell 里实际执行：

```powershell
$env:Path -split ';' | Select-Object -First 15
```

得到的开头是：

```text
C:\Program Files\Common Files\Oracle\Java\javapath
d:\Cursor_download\cursor\resources\app\bin
D:\Cuda\bin
D:\Cuda\libnvvp
D:\Cuda113\bin
D:\Cuda113\libnvvp
D:\vmware\bin\
C:\windows\system32
...
D:\java\jdk17\bin
```

里面**没有**位于最前面的 MSYS2 路径。这说明“用户 Path 列表里的第一条”并非“进程实际 PATH 里的第一条”。

### 4.7 故障处理时间线总结

| 顺序 | 动作 | 观察结果 | 判断 |
|---|---|---|---|
| 1 | 在 VS Code 执行 `g++ --version` | 早期一度找不到命令 | 初始环境未同步 / PATH 未正确生效 |
| 2 | 在 PowerShell 编译 `hello.cpp` | 未生成 `hello.exe` | 进入工具链内部排错 |
| 3 | 运行 `g++ -v` | 已尝试启动 `cc1plus.exe` | 怀疑 C++ 编译前端 |
| 4 | 查看 `$LASTEXITCODE` | `1` | 编译失败 |
| 5 | `cc1plus.exe --version` | `-1073741511` | 动态库函数入口点错误 |
| 6 | 临时把 UCRT64 路径放到 PATH 最前 | `cc1plus` 退出码 `0` | 路径顺序是关键变量 |
| 7 | 重新编译、检查文件、运行 | `0` / `True` / `Hello, C++!` | 临时修复验证成功 |
| 8 | 把路径移动到用户 Path 最前 | 新进程完整 PATH 前部仍是其他系统目录 | 用户 Path 置顶不够 |
| 9 | 最终在**系统变量 Path** 加入该目录并上移到首位 | 本人确认采用此解决办法 | 作为长期方案记录；建议重开终端再次验收 |

## 5. 调试过程与关键证据

这次真正有价值的不是只记住一条修复命令，而是学会**从症状一步步缩小故障范围**。

| 排查命令 | 主要回答什么问题 |
|---|---|
| `g++ --version` | G++ 驱动可否启动？版本是什么？ |
| `where.exe g++` | PATH 中能找到哪些 `g++.exe`？ |
| `Get-Command g++` | PowerShell 实际如何解析 `g++` 命令？ |
| `g++ -v hello.cpp -o hello.exe` | GCC 调用了哪些工具和路径？ |
| `$LASTEXITCODE` | 上一个原生程序是否成功退出？ |
| `Test-Path .\hello.exe` | 目标文件确实生成了吗？ |
| `cc1plus.exe --version` | 故障是否落在 C++ 编译前端本身？ |
| `$env:Path -split ';'` | 当前进程中 PATH 的真实顺序是什么？ |
| `where.exe libwinpthread-1.dll` | PATH 中有没有候选的同名 DLL？ |

**注意两点：**

1. `where.exe <DLL名>` 只能找到 PATH 可见的候选 DLL，**不能证明该进程最终加载的是哪一个**。Windows 的 DLL 搜索还包括程序所在目录、系统目录、已加载模块等机制。若要精确查实际加载过程，可以进一步使用 Process Monitor 等工具。
2. 当前证据足以说明“PATH 顺序变化修复了入口点错误”，但**并不足以断定具体是 `libwinpthread-1.dll`，或具体哪一个软件的 DLL 发生冲突**。

## 6. DLL 原理

### 6.1 DLL 的定义

**DLL = Dynamic-Link Library（动态链接库）**。

可以把 DLL 理解为一个提供可复用代码和数据的模块，其他程序可以在加载或运行时使用它提供的函数。例如：

```text
A.exe ──┐
        ├── 使用 math.dll 中的矩阵计算函数
B.exe ──┘
```

和相关文件对照：

| 文件类型 | 示例 | 含义 |
|---|---|---|
| C++ 源文件 | `hello.cpp` | 人编写的源代码 |
| 目标文件 | `hello.o` | 编译和汇编产生的目标代码，尚待链接 |
| 可执行程序 | `hello.exe` | Windows 可以启动的程序 |
| 动态链接库 | `some-library.dll` | 含可供其他模块调用的代码或数据 |
| 静态库 / 导入库 | `*.a`、`*.lib` | 静态归档或动态库导入信息，具体用途依格式而定 |

**不要混淆：**`#include <iostream>` 是引入头文件中的声明；DLL 则是运行时加载的二进制模块。二者不是同一件事。

### 6.2 程序为什么依赖 DLL？

编译器自己也是程序，并可能依赖其他运行时组件。例如线程支持库、C/C++ 运行时、压缩库等。

程序启动时，Windows 需要解析其依赖的 DLL，并找到要求的函数。如果 DLL：

- 根本不存在：可能是 `STATUS_DLL_NOT_FOUND` 等错误；
- **存在但缺少所需函数入口点**：可能是 `0xC0000139 / STATUS_ENTRYPOINT_NOT_FOUND`；
- 位数不同或不兼容：可能出现其他加载错误。

### 6.3 这次的错误意味着什么？

本次 `cc1plus.exe --version` 返回 `-1073741511`（`0xC0000139`）。可以合理推断：

1. `g++` 驱动程序能启动；
2. 它尝试执行 C++ 编译前端 `cc1plus.exe`；
3. `cc1plus.exe` 的模块加载 / 函数解析遇到错误；
4. 更改 PATH 后它恢复正常；
5. **高度怀疑某个同名 DLL 的版本 / 搜索路径冲突，但具体冲突 DLL 未被直接抓取证实**。

示例（**仅用于说明机制，不代表已经查明是该 DLL**）：

```text
D:\OtherTool\bin\libwinpthread-1.dll       # A 版本
C:\msys64\ucrt64\bin\libwinpthread-1.dll  # B 版本

cc1plus.exe 需要 B 版本提供的某函数
     ↓
如果误加载 A 版本，而 A 没有该函数
     ↓
发生 Entry Point Not Found
```

这里要区分**观测事实**与**推断**：

- 事实：退出码 `0xC0000139`；
- 事实：UCRT64 目录前置后恢复；
- 强推断：DLL 搜索顺序 / 依赖兼容性问题；
- 未证实：具体 DLL 名称、具体冲突软件与准确加载链。

## 7. PATH 与 DLL 搜索机制

### 7.1 PATH 是什么？

`PATH` 是一条由多个目录组成的环境变量，Windows 上各目录通常用分号 `;` 分隔。例如：

```text
C:\Windows\System32;D:\Cuda\bin;C:\msys64\ucrt64\bin
```

在 PowerShell 输入：

```powershell
g++ --version
```

Shell 会按照命令解析规则寻找 `g++`。如果解析为外部可执行文件，就会利用 PATH 等信息定位 `g++.exe`。

如果不知道 PATH，也可以通过绝对路径执行：

```powershell
& "C:\msys64\ucrt64\bin\g++.exe" --version
```

### 7.2 命令搜索与 DLL 搜索不是一回事

**第一种：查找 `g++.exe`**

```text
输入 g++
  ↓
PowerShell 查找别名/命令/可执行文件
  ↓
定位 g++.exe
```

**第二种：`cc1plus.exe` 启动时查找所需 DLL**

```text
cc1plus.exe 启动
  ↓
Windows 加载器解析依赖
  ↓
按适用的 DLL 搜索规则查找动态库
  ↓
若找到不兼容库，则可能产生入口点错误
```

Windows **并不是无条件“优先按照 PATH 查找 DLL”**。对于普通未打包应用，在标准安全搜索模式下，Windows 还考虑 Known DLLs、已加载模块、应用程序所在目录、系统目录、当前目录等，**PATH 所列目录通常在更靠后的位置**。但当搜索确实落到 PATH 时，PATH 内部顺序会影响结果。

所以即使使用 `cc1plus.exe` 的绝对路径启动它，仍可能因为**其依赖或间接依赖的 DLL** 而受 PATH 影响。

微软官方参考：<https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order>

### 7.3 本次发生了什么？

**修改前（简化示意）**：

```text
系统 PATH 的若干软件目录
  → Oracle / CUDA / 其他工具链目录
  → ...
用户 PATH
  → C:\msys64\ucrt64\bin
```

**临时修复后**：

```text
C:\msys64\ucrt64\bin
  → 系统 PATH 原有内容
  → 用户 PATH 原有内容
```

仅改变这个顺序就解决了错误，因此 PATH 对本次问题有决定性影响。

## 8. 最终解决方案

### 8.1 本次最终采用的方式

之前调整的是**用户变量**中的 `Path`，但新终端的完整 PATH 开头依然是 Oracle、Cursor、CUDA 等系统路径。

最终的实际处理方式是：

1. Windows 搜索“**编辑系统环境变量**”，进入“环境变量”；
2. 在下半部分找到 **系统变量（System variables）** → `Path`；
3. 点击“编辑” →“新建”，添加：

   ```text
   C:\msys64\ucrt64\bin
   ```

4. 将该项**上移到系统 Path 的最前面**；
5. 保存，关闭并重新打开 PowerShell / VS Code；必要时重新登录 Windows；
6. 重新执行验证命令。

这是本人后续反馈的**最终选用方案**，与先前临时前置 PATH 后的成功实验原理一致。

### 8.2 建议的永久修复验收命令

新开一个**独立 PowerShell**，不要先执行临时 `$env:Path = ...`，运行：

```powershell
$env:Path -split ';' | Select-Object -First 8
where.exe g++
g++ --version
```

再到项目目录：

```powershell
cd E:\ai-learning\07-inference-and-serving\cuda-learning
& "C:\msys64\ucrt64\lib\gcc\x86_64-w64-mingw32\16.2.0\cc1plus.exe" --version
$LASTEXITCODE

g++ .\hello.cpp -o .\hello.exe
$LASTEXITCODE
Test-Path .\hello.exe
.\hello.exe
```

目标结果：

```text
cc1plus: 退出码 0
编译: 退出码 0
Test-Path: True
Hello, C++!
```

> 这些是**建议复核的预期结果**；原始聊天记录中永久系统 Path 方案实施后没有贴出这组新终端日志。

### 8.3 这个办法的影响和风险

**优点**：对新打开的终端、编辑器更通用，不必每次手动前置路径。

**注意**：系统 Path 是全局配置。计算机上还存在 CUDA、Python、Conda、Java 等环境，把 MSYS2 的库目录全局置顶，可能使其他程序在搜索同名 DLL 或可执行文件时选择不同版本。

因此：

- 目前可以保留这个**已采用且能解释现象**的方案；
- 如果以后其他工具突然出现 DLL 错误，首先想到检查全局 Path 的影响；
- 不要把 `C:\msys64\usr\bin` 也无差别加到全局 Path 首位；
- 更追求隔离性时，可以采用下一节的“项目级 / 终端级”方案。

## 9. 其他修复方案

下面是**替代方案**，并不表示每一种都已经在这台电脑上实际操作成功。

| 方案 | 影响范围 | 是否持久 | 优点 | 注意事项 |
|---|---|---|---|---|
| **A. 系统 Path 置顶（实际采用）** | Windows 整机多数新进程 | 是 | 新开终端通常直接可用 | 可能影响其他开发工具的 DLL 选择 |
| **B. 临时前置 PATH（实际验证成功）** | 当前 PowerShell 及其子进程 | 否 | 最快定位问题、可回滚 | 关掉终端即失效 |
| **C. PowerShell Profile** | 启用了该 Profile 的 PowerShell 会话 | 是（对该 Shell） | 不改系统级 PATH | 不影响 CMD；可能受执行策略影响 |
| **D. VS Code 集成终端配置** | VS Code 新建终端 | 是（对 VS Code） | 适合编辑器内编译 | Tasks / 调试环境要单独确认 |
| **E. MSYS2 UCRT64 终端** | 当前 UCRT64 会话 | 会话内自动配置 | 专用于该工具链，通常更隔离 | 终端语法是 Bash，不是 PowerShell |
| **F. 项目启动脚本** | 脚本启动的 PowerShell/程序 | 每次运行脚本 | 不改变全局环境 | 要从脚本入口启动 |
| **G. 定位冲突 DLL、修复依赖** | 视处理方式而定 | 视处理方式而定 | 从根源治理 | 需要实际加载证据，不要盲目删 DLL |
| **H. MSYS2 更新 / 修复安装** | 编译器软件包本身 | 是 | 适用于工具链包损坏 | 本次已靠 PATH 修复，没证据需要重装 |

### B. 临时前置 PATH：最快的诊断方法 ✅ 实际测试成功

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
g++ .\hello.cpp -o .\hello.exe
```

只改变当前进程环境，适合做“前后对照”。新终端不会自动保留。

### C. PowerShell 启动时自动前置 PATH

运行：

```powershell
$PROFILE
```

检查 Profile 文件位置，必要时创建目录与文件：

```powershell
New-Item -ItemType Directory -Force -Path (Split-Path $PROFILE)
if (-not (Test-Path $PROFILE)) { New-Item -ItemType File -Path $PROFILE | Out-Null }
notepad $PROFILE
```

在配置文件加入：

```powershell
$ucrt = 'C:\msys64\ucrt64\bin'
if (($env:Path -split ';') -notcontains $ucrt) {
    $env:Path = "$ucrt;$env:Path"
}
```

**如果该路径已存在但不在第一位**，上面“避免重复追加”的示例不会将它移动到第一位。要确保始终优先，使用：

```powershell
$ucrt = 'C:\msys64\ucrt64\bin'
$paths = $env:Path -split ';' | Where-Object { $_ -and $_.TrimEnd('\') -ine $ucrt.TrimEnd('\') }
$env:Path = $ucrt + ';' + ($paths -join ';')
```

> 第二段以数组拼接为意图；若要简洁可靠，也可以只保留本次验证过的一行 `$env:Path = "$ucrt;$env:Path"`，其代价是重复启动嵌套 Shell 时可能出现重复路径。注意 PowerShell 5.1 / 7、不同 Windows 用户的 `$PROFILE` 路径可能不一样；如果执行策略阻止加载，需要单独排查，不建议直接大范围放开执行策略。

### D. VS Code 专用 PATH 配置

按 `Ctrl + Shift + P` → **Preferences: Open User Settings (JSON)**。

在已有 JSON 结构中**合并**如下配置（不要覆盖其他原有设置）：

```json
{
  "terminal.integrated.env.windows": {
    "PATH": "C:\\msys64\\ucrt64\\bin;${env:PATH}"
  }
}
```

然后完全关闭旧终端，创建新终端，再查看：

```powershell
$env:Path -split ';' | Select-Object -First 5
```

适合只想在 VS Code 下使用该工具链的情形。需要注意 VS Code 的任务和调试器可能还要配置单独的编译/调试路径，并不保证仅改终端配置就覆盖一切启动方式。

### E. 使用 MSYS2 UCRT64 自带终端

打开 **MSYS2 UCRT64**：

```bash
cd /e/ai-learning/07-inference-and-serving/cuda-learning
g++ hello.cpp -o hello.exe
echo $?
./hello.exe
```

MSYS2 UCRT64 默认会构造自己的工具链环境，通常会让 `/ucrt64/bin` 优先，减少其他 Windows 软件 PATH 的干扰。

### F. 项目级启动脚本

在项目目录创建 `start-cpp.cmd`：

```bat
@echo off
set "PATH=C:\msys64\ucrt64\bin;%PATH%"
powershell -NoExit -Command "Set-Location 'E:\ai-learning\07-inference-and-serving\cuda-learning'"
```

双击脚本，在打开的 PowerShell 中运行编译命令。此脚本只影响从它启动的进程，不更改系统和用户 Path。

### G. 如果要精确找出冲突的 DLL

可以先列出 PATH 上可能存在的同名 DLL：

```powershell
where.exe libwinpthread-1.dll
```

但这**只能提供候选文件**。如需证明真实加载路径：

1. 使用微软 Sysinternals **Process Monitor**（Procmon）观察 `cc1plus.exe` 加载/查找 DLL 的事件；
2. 或使用适合本机的现代依赖分析工具查看导入与实际解析情况；
3. 对比 MSYS2 UCRT64 的 DLL 与其他软件目录的同名 DLL；
4. 找出版本不匹配的根因后，再决定是否隔离 PATH 或修复依赖。

不要直接删除系统 DLL，也不要从不明网站下载 DLL 覆盖现有文件。

### H. 何时考虑重装 / 更新工具链？

只有当 **MSYS2 UCRT64 自带终端也无法运行 `cc1plus`**、程序包缺失或库损坏有较强证据时，再考虑：

```bash
pacman -Syu
pacman -S --needed mingw-w64-ucrt-x86_64-toolchain
```

本次已经证明路径顺序改变就能修复，所以“先重装”不是最高效的办法。

## 10. 三种环境变量

### 10.1 什么是环境变量？

环境变量是操作系统提供给程序的**键值对配置**，典型的有：

```text
USERNAME      = Administrator
TEMP          = C:\Users\Administrator\AppData\Local\Temp
PATH          = C:\Windows\System32;...;C:\msys64\ucrt64\bin
CUDA_PATH     = （若配置了 CUDA，可能存在）
JAVA_HOME     = （若配置了 JDK，可能存在）
```

其中 `PATH` 比较特别：它不是单一路径，而是**用分号隔开的目录列表**。

### 10.2 三个作用域

| 作用域 | 英文名 | 对谁生效 | 是否持久 | 示例 |
|---|---|---|---|---|
| 系统变量 | Machine / System | 该计算机上适用的用户/进程 | 是 | `C:\Windows\System32` |
| 用户变量 | User | 当前 Windows 用户 | 是 | 某个用户自己的 Python 工具目录 |
| 进程变量 | Process | 当前进程及继承其环境的子进程 | 否 | `$env:Path = "...;$env:Path"` |

### 10.3 用户 PATH 第一项为什么不是最终 PATH 第一项？

对于 Windows 的 `Path`，常见的进程环境构造方式是：

```text
Machine Path
    +
User Path
    ↓
进程实际继承的 Path
```

举例：

```text
系统 Path：
  1. C:\Program Files\Common Files\Oracle\Java\javapath
  2. D:\Cuda\bin

用户 Path：
  1. C:\msys64\ucrt64\bin
  2. D:\python311\Scripts

新进程实际 PATH（示意）：
  1. C:\Program Files\Common Files\Oracle\Java\javapath
  2. D:\Cuda\bin
  3. C:\msys64\ucrt64\bin
  4. D:\python311\Scripts
```

所以单纯把 `C:\msys64\ucrt64\bin` 移到**用户变量 Path** 第一位，仍可能无法超过系统变量中的 Oracle / CUDA 路径。这与本次实际观察吻合。

但注意：并不是所有普通环境变量都简单按 Path 的规则拼接；`Path` 在 Windows 上具有特殊合并语义。

### 10.4 如何分别查看三个作用域？

**系统 Path：**

```powershell
[Environment]::GetEnvironmentVariable('Path', 'Machine')
```

**用户 Path：**

```powershell
[Environment]::GetEnvironmentVariable('Path', 'User')
```

**当前 PowerShell 实际 Path：**

```powershell
$env:Path -split ';'
```

**查看前 15 项：**

```powershell
$env:Path -split ';' | Select-Object -First 15
```

**检查 GCC 命令来自哪里：**

```powershell
where.exe g++
Get-Command g++
```

### 10.5 为什么修改环境变量后需要重开 VS Code？

新进程一般从父进程继承环境。已经运行的 VS Code / PowerShell 不一定会自动用新的注册表环境变量替换自己手头的 PATH。

因此出现下列情况并不奇怪：

```text
已在系统环境变量编辑器保存 Path
           ↓
旧 VS Code 仍持有旧环境
           ↓
旧终端中仍出错
           ↓
完全关闭并重开 VS Code / 新建终端
           ↓
得到更新后的环境
```

如仍不一致，可检查 VS Code 是不是由旧进程启动，或从终端手动启动导致继承了不同 PATH。必要时注销并重新登录 Windows，再验证。

## 11. GCC 编译调用链

### 11.1 分阶段看

```text
hello.cpp  （C++ 源代码）
    │
    │  g++ 作为驱动程序组织整个流程
    ▼
[1] 预处理：展开 #include、宏等
    │
    ▼
[2] C++ 编译前端 cc1plus：语法/语义分析、优化、生成汇编
    │
    ▼
hello.s   （汇编代码）
    │
    ▼
[3] 汇编器 as：汇编为机器代码与目标文件
    │
    ▼
hello.o   （目标文件）
    │
    ▼
[4] 链接器：结合启动代码、其他目标文件、需要的库
    │
    ▼
hello.exe （Windows 可执行文件）
```

> 这是便于学习的逻辑链路；实际 GCC 驱动可能合并或调整前端阶段、使用 `collect2` 或直接调用链接器，并依据配置决定具体程序名称。

### 11.2 为什么 `g++ --version` 正常，还可能编译失败？

因为查看 G++ 版本号不一定启动 `cc1plus.exe`、`as.exe`、链接器，也不一定加载它们各自的运行时依赖。

因此：

- `g++ --version` 成功：G++ 驱动本身可以运行；
- `g++ hello.cpp ...` 失败：可能是预处理、C++ 前端、汇编或链接中的任一阶段；
- `cc1plus.exe --version` 失败：问题已经进一步定位到 C++ 前端的加载/运行条件。

### 11.3 学习时可以主动拆开编译过程

**预处理（生成 `.ii`）：**

```powershell
g++ -E hello.cpp -o hello.ii
```

**只生成汇编（`.s`）：**

```powershell
g++ -S hello.cpp -o hello.s
```

**只编译到目标文件（`.o`）：**

```powershell
g++ -c hello.cpp -o hello.o
```

**链接生成 exe：**

```powershell
g++ hello.o -o hello.exe
```

**一次性编译链接：**

```powershell
g++ hello.cpp -o hello.exe
```

以后学习 `llama.cpp` 的 CMake 构建、Kernel 编译、静态库与动态库时，这个分阶段模型很重要。

### 11.4 为调试生成符号信息

```powershell
g++ -g -O0 hello.cpp -o hello.exe
```

- `-g`：保留调试信息；
- `-O0`：关闭优化，方便源码级单步调试；
- `-o`：指定输出文件。

安装了 GDB 并在 VS Code 配好调试器之后，就可以打断点、查看局部变量和调用栈。

### 12.2 这次最重要的三条经验

1. **命令能找到，不代表工具链就能完成任务**：`g++.exe` 和 `cc1plus.exe` 是不同程序，依赖可能不同。
2. **不要只看屏幕有没有红字**：应结合 `$LASTEXITCODE`、目标文件存在性、详细日志、最小对照实验。
3. **解决环境问题要区分作用域**：用户 Path、系统 Path、当前进程 Path 不同；全局置顶能解决问题，但也可能引入新的冲突。
